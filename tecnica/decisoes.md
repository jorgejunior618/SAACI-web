# Decisões

Registro do **porquê**. O "como" está nos outros documentos; o "o quê"
está no código.

## Arquitetura

| Decisão                                                                 | Por quê                                                                                                                                                                                                                                                 | Descartado                               |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Supabase é o backend, sem API própria de CRUD                           | O PostgREST já expõe o schema como REST; uma camada Next na frente empilharia duas APIs                                                                                                                                                                 | Route Handler por entidade               |
| `app/api/` só para segredo e agendamento                                | São os dois casos em que o Next acrescenta algo                                                                                                                                                                                                         | —                                        |
| Escrita financeira multi-tabela em RPC transacional                     | Queda de rede no meio da alocação deixaria pagamento gravado sem abater pedido; público-alvo tem sinal instável                                                                                                                                         | Sequência de writes em TypeScript        |
| Leitura agregada no Postgres                                            | Relatório pelo cliente exigiria trafegar a base inteira; a diferença medida é de ordens de grandeza                                                                                                                                                     | Agregação em TypeScript                  |
| `services/` é a fronteira; `@supabase` fica fino                        | Com a regra de negócio em SQL, um adapter em TS não protegeria de migração — o acoplamento está no SQL                                                                                                                                                  | Ports & Adapters completo por domínio    |
| Auth atrás de porta própria                                             | É a peça com maior chance real de troca                                                                                                                                                                                                                 | —                                        |
| `salvar_produto` (Fase 8) em RPC transacional, mesmo sem ser financeira | Salvar produto grava em três tabelas (`produtos`, `unidades`, `variacoes`); três escritas soltas do service deixariam um produto sem unidade se a conexão caísse no meio — mesmo motivo mecânico da RPC de pagamento, aplicado a um caso não financeiro | Três `insert`/`update` soltos do service |

## Front-end

| Decisão                                                                           | Por quê                                                                                                                                                                                                         | Descartado                                                               |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| RSC faz prefetch, React Query assume                                              | Corta uma viagem de rede na entrada de cada tela                                                                                                                                                                | Busca só no cliente                                                      |
| `app/` fino + `src/features/`                                                     | Componente não fica preso à convenção de arquivos do Next                                                                                                                                                       | Co-location dentro de `app/`; `modules/screens`                          |
| Panda CSS                                                                         | Zero runtime e funciona em Server Component sem `'use client'`                                                                                                                                                  | Tailwind; CSS-in-JS com runtime                                          |
| Valibot                                                                           | Bundle menor com a mesma ideia de schema como fonte do tipo                                                                                                                                                     | Zod                                                                      |
| `@design-system` com níveis atômicos                                              | Torna explícito o critério de promoção                                                                                                                                                                          | Pasta plana de componentes                                               |
| Recharts                                                                          | Dois eixos Y nativos, e a biblioteca só carrega nas rotas de dono em desktop                                                                                                                                    | Chart.js; visx                                                           |
| Vitest                                                                            | Mais rápido que Jest, com API equivalente                                                                                                                                                                       | Jest                                                                     |
| Shell em `components/`, não em `@design-system/templates` (Fase de shell)         | `AppShellDono`/`AppShellFuncionario` precisam de `usePathname()`, `next/link` e do perfil da sessão — exatamente o que `@design-system` proíbe (UI pura, sem rede/rota); `templates/` segue vazio               | Template em `@design-system` recebendo tudo por prop                     |
| Folha do Menu é `Modal placement="sheet"`, não componente novo (Fase de shell)    | `Modal` já resolve o difícil (`<dialog>` nativo: foco preso, `::backdrop`, `Esc`); uma `BottomSheet` à parte reimplementaria isso em `<div>`, a origem mais comum de modal inacessível (`doc/design-system.md`) | `BottomSheet` própria, com foco controlado à mão                         |
| Lateral × barra de baixo alternam por CSS, nunca `useMediaQuery` (Fase de shell)  | Decidir a forma em JavaScript renderiza a errada no servidor e troca depois da hidratação — pisca em toda entrada; as duas navegações ficam no DOM, uma escondida por `@media`                                  | Detectar largura em JS e renderizar condicionalmente                     |
| Casca de formulário (`FormularioLancamento` do protótipo) não promovida na Fase 8 | Promovê-la agora exigiria refatorar `FormularioCliente`, tela recém-entregue e testada, a partir de só dois casos; Pedidos (Fase 9) é o terceiro e o mais diferente dos três — é ele que revela a forma certa   | Promover com dois casos só; deixar `FormularioProduto` sem casca nenhuma |
| Catálogo usa cartão nas duas larguras, não `DataTable` (Fase 8)                   | O conteúdo de um produto é uma hierarquia de duas listas (unidades, variações), não uma linha de colunas fixas — `DataTable` (Fase 7) não encaixa                                                               | `DataTable` com célula de chips                                          |
| `useSuspenseQuery` é o padrão; `useQuery` vira exceção comentada                  | `useQuery` devolve `data: undefined` no erro, e o default `= []` ao lado transformava falha de rede em lista vazia — a tela oferecia "cadastre o primeiro produto" a quem já tem trinta                         | Manter `useQuery` com default; tratar `isError` tela a tela              |
| Query condicional divide o componente, em vez de `enabled`                        | `useSuspenseQuery` não tem `enabled`. Dividir apaga junto o `if (!dado) return null` e o risco do `defaultValues` do React Hook Form, que é lido uma vez só e congelaria vazio se o form montasse antes do dado | `useQuery` + `enabled` nos formulários; `useSuspenseQuery` com id vazio  |
| Busca e filtro continuam em `useQuery` (`ListaClientes`)                          | `useSuspenseQuery` não aceita `placeholderData` — sem `keepPreviousData`, a tabela sumiria atrás do fallback a cada tecla digitada                                                                              | Suspense com `useDeferredValue` para segurar a árvore anterior           |

## Dados

| Decisão                                                                                                     | Por quê                                                                                                                                                                                                                                                                       | Descartado                                                                                           |
| ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Banco em português; verbo em inglês no TS                                                                   | Tabela fala a língua do negócio; código segue a convenção usual                                                                                                                                                                                                               | Tudo em inglês; tudo em português                                                                    |
| `pagamentos` e `despesas`                                                                                   | O modelo tem baixa por pedido e é conceitualmente diferente do sistema anterior; nome novo evita confundir os dois                                                                                                                                                            | `financeiro_entradas` / `financeiro_saidas`                                                          |
| Vínculo N↔N com `valor_aplicado`                                                                            | Um pagamento cobre vários pedidos e um pedido recebe vários pagamentos; FK em qualquer um dos lados quebra                                                                                                                                                                    | FK direta entre as tabelas                                                                           |
| `valor_pago` mantido pela RPC + status como coluna gerada                                                   | Filtro por status fica indexado, e o status nunca diverge do valor                                                                                                                                                                                                            | Status calculado em view a cada leitura                                                              |
| Crédito derivado do que não foi alocado                                                                     | Nenhuma coluna nova para manter em sincronia                                                                                                                                                                                                                                  | Coluna de saldo no cliente                                                                           |
| Competência não existe **na receita**                                                                       | A alocação por pedido já responde a que venda o valor pertence                                                                                                                                                                                                                | Herdar do sistema anterior                                                                           |
| Despesa tem `mes_competencia`; receita, não (revisão)                                                       | Despesa não tem alocação que responda a que mês ela pertence, e a cliente relatou o caso real ("comprei hoje, usei o dinheiro do mês passado"); a decisão anterior tinha avaliado só a receita e ficou escrita de forma genérica demais                                       | Competência em toda tabela financeira; coluna gerada de `data_despesa` (mataria o poder de divergir) |
| Uma tela, um eixo: Relatórios só por `data_despesa`, Fechamento do mês só por competência                   | Dois critérios de data na mesma tela produzem dois totais de despesa diferentes, e quem lê conclui que o sistema errou. Repete o padrão já aplicado em Contas a Receber, que virou módulo próprio pela mesma razão (métrica deliberadamente diferente)                        | Eixo misto dentro de Relatórios; seletor de "contar por qual data"                                   |
| Excluir cliente com histórico continua bloqueado, nunca `cascade` (Fase 7, decisão E1)                      | Apagar o cliente levaria pedidos e pagamentos junto — um clique desfaria o faturamento de um período inteiro, sem erro visível na tela nem no relatório                                                                                                                       | `on delete cascade` em `pedidos.cliente_id`/`pagamentos.cliente_id`                                  |
| Catálogo usa soft delete em todo item, nunca hard delete (Fase 8, decisão D2)                               | O schema já nasceu assim (Fase 3); "excluir" precisa continuar resolvendo o nome em pedido/pagamento/despesa antigos — diferente de `clientes`, cuja exclusão é rara e definitiva                                                                                             | Hard delete com `on delete restrict`, como em `clientes`                                             |
| `unidades` continua linha por produto; vocabulário fixo vive na tela, não no banco (Fase 8, decisão D8)     | Reestruturar para um vocabulário de sistema tocaria `pedido_itens.unidade_id`, a tabela que a Fase 9 consome logo em seguida — exatamente o risco que o roadmap nomeou ("inverter isso obriga a refazer o formulário de venda depois")                                        | Tabela de vocabulário fixo + junção `produto_unidades`, com FK de `pedido_itens` migrada             |
| Variação é obrigatória, como unidade (Fase 8, decisão D9, revertida)                                        | Decisão revertida a pedido explícito, depois de uma primeira versão ter tornado variação opcional. `pedido_itens.variacao_id` continua nulo no schema (Fase 3) — a obrigatoriedade é do produto ter ao menos uma variação cadastrada, não de todo item de pedido escolher uma | Variação opcional (primeira versão desta fase, revertida)                                            |
| Forma de pagamento e categoria de despesa nascem preenchidas; produto e local, vazios (Fase 8, decisão D10) | Divisão por quem é dono do vocabulário: as duas primeiras são comuns a qualquer fazenda (Dinheiro, Pix…), as outras duas são específicas da fazenda — pré-preencher local de venda entregaria exemplos que a organização teria de apagar                                      | Provisionar as quatro listas; não provisionar nenhuma                                                |

## RLS e permissões (Fase 5)

| Decisão                                                                                                     | Por quê                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Descartado                                                                                                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Função de contexto lê `auth.jwt()`, `security invoker`                                                      | A Fase 4 já grava papel/organização como claim; ler do token não é consulta, então o risco de recursão em `profiles` desaparece por construção, sem precisar de privilégio elevado                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | `security definer` consultando `profiles` (desenho original do doc, anterior à Fase 4)                                                                                                                                                   |
| Capacidades individuais são colunas em `profiles`, viram claim                                              | São duas, independentes; ler do JWT custa zero por consulta e mantém uma fonte de verdade só                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Policy consultando `profiles` via função `security definer`; tabela `capacidades` N↔N                                                                                                                                                    |
| Capacidade nunca abre leitura, só escrita — sem capacidade de "ver" separada                                | Uma leitura do financeiro, mesmo desacoplada de "lançar", abriria o caixa inteiro da organização para quem só devia lançar                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Capacidade `pode_ver_financeiro` independente (avaliada e descartada em conversa)                                                                                                                                                        |
| RPC de alocação de pagamento (Fase 10) será `security definer`, exceção nomeada                             | Funcionário com capacidade não lê pedido alheio, mas a alocação precisa varrer todos os pedidos em aberto do cliente                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | RLS de `invoker` puro (deixaria a alocação sem o que alocar, silenciosamente)                                                                                                                                                            |
| Escrita do funcionário é append-only — revisão de D8 (08/08/2026)                                           | D8 deixava ele editar o próprio pedido e recusava só o soft delete; na prática isso é reescrever a venda depois de gravada, e o dono perde a única versão do que foi lançado em campo. Correção passa pelo dono, que já é quem responde pelo número                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Janela de correção de alguns minutos após o lançamento (some a garantia e sobra um relógio para explicar a quem levou "não dá mais")                                                                                                     |
| Item de pedido travado por `xmin`, com o RLS continuando `invoker`                                          | Sem trava, o funcionário acrescenta item a uma venda antiga dele e muda o total — a mesma edição, por outra tabela. `p.xmin = pg_current_xact_id()::xid` responde "este pedido nasceu nesta transação?", que nenhuma transação concorrente consegue mudar                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | RPC `salvar_pedido` em `security definer` com `revoke` (fecharia igual, mas tira o RLS da escrita e joga a checagem de organização para código à mão); trava por "o pedido ainda não tem item" (dois inserts simultâneos passam os dois) |
| Formulário de pedido com um item, RPC com contrato de N (Fase 9, decisão A1)                                | O banco é 1:N desde a Fase 3 e a Home do funcionário já promete "3 itens", mas o protótipo de lançamento tem um produto só. Guardar N no contrato e 1 na tela custa nada agora; refazer a assinatura depois arrastaria a Fase 10, que aloca pagamento contra o total do pedido                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Formulário de N itens já nesta fase (desenho que o protótipo não tem, e mais toque numa tela usada em pé, no sol); achatar `pedido_itens` dentro de `pedidos` (mataria seed, policies testadas e a alocação)                             |
| Número do pedido vem de contador por organização (Fase 9, decisão B1)                                       | Numeração densa por fazenda é o que o dono lê no telefone. O `update ... returning` serializa lançamentos da mesma organização, mas na escala real (dezenas/dia) a espera é de milissegundos                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Sequence global (cada fazenda veria os próprios números pularem, e isso vaza volume agregado); sequence por organização (exigiria `create sequence` em runtime, com DDL fora de migration)                                               |
| Número atribuído por trigger `security definer`, não dentro da RPC (Fase 9)                                 | `organizations` só tem `grant select` (Fase 5), então `update` ali em função `invoker` é recusado no privilégio de tabela. Como trigger, o número passa a valer para todo caminho de escrita — seed e RPCs futuras inclusive                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | `grant update (proximo_pedido) to authenticated` (deixaria o contador ao alcance de escrita direta; zerá-lo travaria toda gravação seguinte no índice único)                                                                             |
| Offline é rascunho local com reenvio manual (Fase 9, decisão C1)                                            | O critério do roadmap é "não redigitar", e `localStorage` cumpre isso inteiro — inclusive se o aparelho desligar, que fila de sincronização sozinha não cobre                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Service Worker + Background Sync (exige idempotência na RPC, e não existe no Safari do iPhone: o texto "sobe sozinho" seria falso em boa parte dos aparelhos do público)                                                                 |
| Local da venda obrigatório na RPC, nulo no schema (Fase 9, decisão F1)                                      | Regra de produto muda; constraint com dado gravado exige migration para afrouxar. E existe histórico de planilha sem local anotado, que `set not null` fecharia a porta para importar                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | `alter column local_venda_id set not null`                                                                                                                                                                                               |
| `atualizar_pedido`/`remover_pedido` checam papel e lançam LID25                                             | Não é autorização — quem autoriza é a policy. É que a recusa do RLS é silenciosa (zero linhas, sem erro): sem o `raise`, a tela do funcionário mostraria "Pedido salvo" com nada gravado                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Confiar só no RLS (o silêncio vira sucesso falso na tela)                                                                                                                                                                                |
| Corrigir pedido faz soft delete dos itens antigos, não `update` neles                                       | Preço e quantidade cobrados antes da correção são histórico financeiro; sobrescrever apagaria o que foi cobrado                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `update` no lugar (mais barato, e perde a versão anterior da venda)                                                                                                                                                                      |
| Guard de papel vai na barra de ações inteira, nunca botão a botão (09/08/2026)                              | O mesmo defeito apareceu duas vezes no protótipo (Tela 06 e Tela 07): quem escreveu guardou o botão destrutivo e esqueceu o de edição — "remover" parece mais perigoso, mas os dois escrevem, e a recusa da edição é a silenciosa. Um guard só no bloco fecha a classe inteira                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Guard por botão (foi o que produziu os dois defeitos); confiar em code review para lembrar de cada botão novo                                                                                                                            |
| "Prazo (fiado)" não é forma de pagamento — some da Tela 07 (09/08/2026)                                     | Fiado é a **ausência** de pagamento; a dívida já é o pedido em aberto. Como forma, viraria um pagamento sem dinheiro entrando: aloca contra os pedidos abertos, marca como pagos e zera a dívida — corrompendo em silêncio a Fase 12, que é a tela de quem está devendo                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Manter na lista (a decisão já estava em `modelagem-dados.md`; o protótipo é que divergiu); criar um tipo de pagamento "sem valor" para representar fiado                                                                                 |
| Correção de pagamento realoca o cliente inteiro, em cascata (Fase 10, decisão A1)                           | Cinco operações mexem em dinheiro distribuído (registrar, corrigir e remover pagamento, corrigir e remover pedido com pagamento); cinco implementações da mesma distribuição seriam cinco chances de uma divergir, e a que divergisse produziria o total que não bate. A cascata é uma função só, e faz "os totais fecham" virar propriedade do desenho em vez de lista de casos a lembrar. Custo aceito de olhos abertos: reescreve qual pagamento quitou qual pedido, e esse pareamento é impresso pelo extrato (Fase 11) e mandado por WhatsApp                                                                                                                                                                                                                                                            | Realocação mínima só do delta (preserva o pareamento histórico, ao custo de casos de borda — de qual pagamento sai o troco quando dois parciais quitaram o pedido? — e cada caso de borda é onde o centavo some)                         |
| `registrar_pagamento` também chama a cascata, em vez de um algoritmo incremental (Fase 10)                  | O incremental empata com a cascata só quando o pagamento novo é o mais recente do cliente. Um lançamento **retroativo** precisa entrar na fila antes dos posteriores, mudando o pareamento deles — e com dois algoritmos, o retroativo é o caso que um deles esquece                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Alocar só o pagamento novo contra os saldos atuais                                                                                                                                                                                       |
| Retorno de `registrar_pagamento` recortado por papel: o funcionário recebe só o eco (Fase 10, decisão A2)   | A função é `definer` e PODE devolver os pedidos do cliente. Qualquer coisa derivada deles — até a contagem "abateu 2 pedidos" — é volume de venda, e reabriria pelo retorno da função a leitura que a Fase 5 fechou pela ausência de policy. O eco puro é a única opção em que o recorte não depende de julgar quanto é "pouca informação"                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Eco + contagem sem valores; eco + aviso de sobra sem o valor                                                                                                                                                                             |
| Sem constraint `valor_pago <= total`; lock de linha + conferência na função (Fase 10, decisão A4)           | A cascata passa por estados intermediários inválidos (zera tudo, redistribui), que uma constraint imediata rejeitaria; contorná-la exigiria `deferrable initially deferred`, um conceito a mais para manter. A conferência na função produz erro de domínio traduzível (LID36)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | `check (valor_pago <= total)`, imediata ou deferrable                                                                                                                                                                                    |
| `realocar_pagamentos_do_cliente` lê `org_atual()` em vez de receber a organização (Fase 10)                 | `atualizar_pedido`/`remover_pedido` são `invoker` e precisam chamá-la, o que exige `grant` a `authenticated`. Com a organização vindo por parâmetro, qualquer autenticado reescreveria o pareamento de OUTRA fazenda — a função é `definer`, o RLS não a barraria. Lendo a organização de dentro, o alcance máximo de uma chamada por fora é a própria, onde o efeito é idempotente                                                                                                                                                                                                                                                                                                                                                                                                                           | Tornar `atualizar_pedido`/`remover_pedido` `definer` (jogaria fora policies testadas na Fase 9); manter sem `grant` (não compila o caminho de correção)                                                                                  |
| Pagamento tem número próprio, com contador por organização (Fase 10, achado N1)                             | O protótipo identifica cada linha por `#901` e o detalhe se chama "Pagamento #901" — `id` é uuid, e ninguém lê uuid no telefone. Mesma decisão B1 do pedido, pelas mesmas razões. Não estava em nenhum documento: apareceu ao ler o desenho                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Reaproveitar o `id`; sequence global                                                                                                                                                                                                     |
| ~~Crédito só exibido, nunca consumido automaticamente~~ **REVOGADA na Fase 10.1** (era Fase 10, decisão A6) | **Ficava registrada uma regra que o código não cumpria.** A cascata da A1 consumia o crédito de qualquer forma — só que na PRÓXIMA escrita qualquer naquele cliente, não no lançamento do pedido. O dono lia "Virou crédito R$ 50,00", voltava dois dias depois e não via mais, sem ter feito nada relacionado. Pior: entre o pedido novo e a escrita seguinte, o cliente ficava com crédito E dívida ao mesmo tempo — o estado que a própria conferência LID36 recusa quando ela o produziria. A objeção original ("faz um pedido nascer parcialmente pago sem ninguém ter registrado pagamento") era boa, mas descrevia algo que já acontecia; o que faltava era acontecer à vista. Fica registrada em vez de apagada: a decisão errada e o porquê de ela ter sido tomada valem mais que a correção sozinha | Fazer a A6 virar verdade, impedindo um pagamento de alcançar pedidos posteriores a ele (mexeria no laço da cascata recém-testado e criaria caso de borda no lançamento retroativo, que é o cenário que justificou a A1)                  |
| `salvar_pedido` redistribui o dinheiro do cliente ao gravar (Fase 10.1, decisão C1)                         | Fecha a contradição acima: o crédito entra no pedido na mesma transação em que ele nasce. `atualizar_pedido` e `remover_pedido` já faziam isso desde a Fase 10; era `salvar_pedido` que estava de fora. **Ganho colateral:** o estado "crédito e dívida ao mesmo tempo" deixa de ser alcançável, e a terceira invariante da LID36 passa a valer para o sistema inteiro em vez de só dentro da função (caso P21)                                                                                                                                                                                                                                                                                                                                                                                               | Deixar como estava (o efeito vinha de qualquer jeito, atrasado e invisível)                                                                                                                                                              |
| A confirmação de crédito usado aparece só quando houve crédito (Fase 10.1, decisão C2)                      | Um modal em toda venda vira clique automático em duas semanas, e aí deixa de informar inclusive nos casos em que teria algo a dizer. É a raridade que o mantém legível. Sem crédito, o fluxo segue direto para o detalhe, como sempre foi                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Aviso fixo no detalhe do pedido (a pessoa passa direto, e o aviso fica para sempre); só toast (some em 4s e não mostra a conta)                                                                                                          |
| O funcionário dispara a realocação, mas não a enxerga (Fase 10.1)                                           | O pedido precisa entrar na fila independentemente de quem o lançou, senão o dono veria número errado até a próxima escrita. Que ele não veja o resultado é assunto da tela, não da função: `showValues`/`showPayment` já chegam `false` na rota de campo, e o modal fica atrás de `shell === 'dono'`. ### Revisão do recorte — "conta atual" (12/08/2026)

Uma decisão da própria fase, revista depois de pronta e testada. Registrada
como a Fase 10.1 registrou a revogação da A6: **a decisão errada fica
escrita, não apagada** — a objeção original era razoável no papel, e o que
faltava era ver o que ela produz num cliente real.

|                      |                                                                                                                                                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dizia**            | Recorte padrão "a partir da última vez que a conta zerou" — palavras do roadmap, e o que a primeira migration implementou                                                                                                                |
| **Produzia**         | Num cliente que paga sempre atrasado, o saldo acumulado zera uma vez e nunca mais: o extrato abria meses antes, num pedido pago havia tempo. No cliente de 40 lançamentos do seed, 38 de 40 linhas — um recorte que não recorta          |
| **Passa a dizer**    | Começa no **pedido mais antigo ainda não quitado** — corte de estado, não de tempo. E é inclusivo: esse pedido é a primeira linha                                                                                                        |
| **Por que é seguro** | Se o saldo zerou em T, então pagamentos(≤T) ≥ pedidos(≤T) e a cascata FIFO quitou tudo até T. O pedido mais antigo em aberto é sempre igual ou posterior ao corte antigo: o recorte novo nunca mostra mais, e nunca abre num pedido pago |
| **Medido**           | Hortifruti 38 → 12, Sacolão 6 → 5, Restaurante 3 → 2; os outros quatro inalterados. Identidade do documento continua fechando nos 14 pares cliente × recorte                                                                             |

**O que o cenário revelou.** O número nunca esteve errado — a dívida, os
totais e o documento sempre fecharam. O defeito era de **recorte**: a tela
respondia "desde quando existe conta" quando a pergunta é "desde quando
existe dívida". São perguntas diferentes, e a segunda é a que ela faz antes
de ligar cobrando.

**O que saiu junto.** `credito_no_corte` (media o quanto o saldo passou de
zero — conceito que só existe num corte temporal; o que a tela precisa
dizer já está em `abatido_de_fora`) e `conta_vazia` do SQL (derivável de
`tem_aberto` e `quantos_cliente`; dois campos que precisam concordar são
dois campos que podem discordar, então quem os compõe agora é o service).

**A função trocou de nome** — `extrato_corte_do_cliente` →
`extrato_inicio_da_conta_atual` — de propósito. O corte antigo era
exclusivo, o início novo é inclusivo, e mudar essa semântica mantendo o
nome é o tipo de coisa que passa despercebida em quem só lê a chamada.
Renomear obrigou a revisitar as 22 chamadas, que era o efeito desejado.

## Contas a receber (Fase 12)

| Decisão                                                                                         | Por quê                                                                                                                                                                                                                                                                                                                        | Descartado                                                                                                                                |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **E1** — ritmo é a **mediana** do intervalo entre pagamentos, não a média                       | Um cliente que pagou em 3, 4, 5 e 90 dias tem média 25,5 e mediana 4,5. Com a média, uma única ausência longa reescreve o "normal" dele — e ele passa a parecer em dia justamente quando some. A mediana ignora o extremo, que é o comportamento que a tela existe para acusar. Fecha a pendência aberta desde a Fase 9        | Média (absorve a anomalia); moda (sem sentido em dias corridos)                                                                           |

Quinta origem de `BotaoExtrato`, que já a previa no TSDoc                                                                                                                            | Redesenhar um mini-extrato dentro desta tela (proibido explicitamente pelo documento de produto)                                          |

### I14 — a linha "Ajustes de meses anteriores" foi removida (15/08/2026)

Ela entrou com a fase (I2, I6) e saiu no mesmo dia, depois da primeira
leitura da tela pronta. O motivo não foi estético: **ela só acertava sob
uma condição que o sistema não enxerga.**

| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **O que ela fazia**                       | Descontava do mês exibido as saídas lançadas nele com referência em mês anterior, para corrigir um mês que já tinha sido dividido pelo número antigo — o erro se corrigia sozinho no mês seguinte, sem ninguém devolver nada                                                                                                                                                                                                                                               |

## Endereço errado e identidade da aba (pós-Fase 13)

| Decisão                                                                               | Por quê                                                                                                                                                                                                                                                                                                                                                                        | Alternativa descartada                                                                                                                            |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **G1** — rota com segmento dinâmico valida o formato do param **antes** do prefetch   | Param malformado faz o Postgres recusar o cast, a RPC estoura, `prefetchQuery` **engole** o erro, e o `useSuspenseQuery` da tela busca sozinho no servidor — caindo no cliente de browser. A pessoa recebe um erro sobre `createClient` quando o que houve foi uma URL inválida. Medido: com guard 0, sem 2                                                                    | Deixar o service tolerar lixo (esconde erro real); confiar no `notFound()` da tela (não é alcançado, a rota quebra antes)                         |
| **G2** — `isSafeInteger(n) && n > 0`, não `isInteger`                                 | `Number('9999999999999999999')` é inteiro, passa, e o Postgres recusa com `22003` — o mesmo engolir-e-quebrar por outra porta. O `> 0` recusa `/pedidos/0` e negativos, que iam ao banco sem precisar                                                                                                                                                                          | Só `isInteger` (deixa a faixa aberta); validar no service (a rota quebra antes de chegar lá)                                                      |
| **G3** — `getClienteById` devolve `Cliente \| null`, com `maybeSingle`                | `.single()` trata ausência como erro, e um id de cliente inexistente lia "Não deu para carregar esta tela" — a frase de queda de conexão, sobre um cliente que nunca existiu. Os outros três domínios já devolviam `null`; clientes era o único fora do padrão                                                                                                                 | `try/catch` no `PGRST116` (traduz um código para dizer o que a API já sabe dizer); manter `.single()` (mantém a divergência)                      |
| **G4** — `not-found.tsx` por **entidade**, dentro do segmento                         | `notFound()` não carrega dado: sobe até o arquivo mais próximo, e é a posição dele na árvore que diz qual entidade era. O de `[numero]/` cobre `[numero]/editar/` junto                                                                                                                                                                                                        | Um componente lendo a entidade do `usePathname()` — troca seis arquivos declarativos por uma tabela de regex que erra em silêncio em rota nova    |
| **G5** — o botão do 404 de entidade volta para a **lista**, não para o início         | O genérico manda para `/inicio` porque não sabe de onde a pessoa veio. O de entidade sabe: quem digitou `/pedidos/9999` quer pedidos, e o início o obrigaria a refazer a navegação inteira                                                                                                                                                                                     | Destino único para todos                                                                                                                          |
| **G6** — metadata em `not-found.tsx` de segmento **não é escrita**, por não funcionar | Quando `notFound()` é lançado de dentro de uma página, o `<title>` daquela página já foi resolvido e enviado — o metadata do desvio chega tarde. Medido em 14/08/2026. Um metadata inerte ali seria pior que nenhum: quem lesse acreditaria que a aba diz outra coisa                                                                                                          | Deixar o export inerte; `generateMetadata` com consulta ao banco em cada rota de detalhe, só para acertar o título de um caso raro                |
| **G7** — `title: { default, template: '%s · Lida' }` e título por página              | Só o layout raiz definia título, então **toda** aba dizia "Lida" e três telas abertas eram indistinguíveis. Com `template`, cada página exporta só o próprio nome e o sufixo mora num lugar só                                                                                                                                                                                 | Título repetido em cada arquivo; título único no raiz (o que havia)                                                                               |
| **G8** — os títulos da aba são escritos à mão, não derivados de `navigation.ts`       | O menu diz **para onde ir** ("Despesas"); a aba diz **onde você está**, que num formulário é "Lançar saída". `SUB_ROUTE_TITLES` já existe separado pela mesma razão                                                                                                                                                                                                            | Reusar `OWNER_NAV` (obrigaria a rota de criar a se chamar como a lista, ou um terceiro campo que só a aba lê — a mesma duplicação, escondida)     |
| **G10** — modal de confirmação tem **duas saídas nomeadas**, sem X e sem clique fora  | O modal é RECIBO, não pergunta: o registro já está gravado quando ele abre, e sair é escolher **entre destinos** ("Lançar outro" ou "Ver"), não dispensar. Um X ou um clique fora escolheria um dos destinos sem a pessoa saber qual. Vale nas três telas — saída, pagamento e pedido                                                                                          | Um botão só (obriga a passar pelo detalhe entre dois lançamentos seguidos); X no topo (vira a terceira saída, sem destino declarado)              |
| **G11** — o `onClose` mora no `Modal`, e o botão só manda fechar                      | O evento nativo do `<dialog>` cobre botão e `Esc` num caminho só. A intenção de saída viaja num `ref`, e `'ficar'` é o padrão do `Esc` | Cada botão duplicando a limpeza (o `Esc` continua fora); bloquear o `Esc` (deixa preso quem não usa mouse dentro de um diálogo que prende o foco) |
| **G12** — o formulário é limpo ao FECHAR o modal, não no submit                       | Limpar no submit esvaziava a tela no instante em que a confirmação abria: quem fechava encontrava tudo em branco e concluía que tinha perdido o que digitou. O rascunho, ao contrário, é descartado no submit — o registro já existe, e um rascunho sobrevivente convidaria a lançar de novo o que já entrou                                                                   | Limpar nos dois momentos; não limpar (deixa o formulário pronto para duplicar)                                                                    |
| **G9** — o ícone é um `path` desenhado, não texto na fonte da marca                   | O `Wordmark` é "Lida" em Caveat, carregada por `next/font/google` — fonte que existe no CSS e **não** dentro de um SVG. Um `<text font-family="Caveat">` renderizaria com o fallback do sistema na aba, no favorito e no atalho                                                                                                                                                | `icon.tsx` com `ImageResponse` rasterizando a fonte (exige carregar o arquivo da fonte em tempo de build); manter o favicon padrão do Next        |

## Segurança de acesso (Fase 16)

Quatro decisões tomadas juntas, depois que a tela de equipe ficou pronta e
a pergunta "estamos seguros?" foi feita. Todas medidas antes de aplicar —
a bateria de integração rodou verde com cada uma.

| Decisão                                                          | Por quê                                                                                                                                                                                                                                                                                                 | Alternativa descartada                                                                                                            |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **S1** — `enable_signup = false`                                 | A premissa "não existe autocadastro" era **falsa**: com a chave `anon`, pública, um `curl` criava organização inteira e entrava como dono. Corrigido e travado por teste (A1/A2)                                                                                                                        | Confiar no gatilho (barrava só quem esquecesse o campo `nome` — proteção por acidente)                                            |
| **S2** — `secure_password_change = true`                         | Sem isto, quem alcança uma sessão aberta troca a senha e toma a conta. Medido: não atrapalha o primeiro acesso, porque quem acabou de logar satisfaz o "logged in recently"                                                                                                                             | Deixar `false` (um passo a menos, ao custo de celular esquecido = conta perdida)                                                  |
| **S3** — senha de **8 caracteres, com letra e dígito**           | Comprimento é o que mais protege contra força bruta. A régua vive em `src/constants/senha.ts` e espelha `password_requirements` do GoTrue — antes o número `6` estava escrito em cinco lugares                                                                                                          | `lower_upper_letters_digits_symbols` (produz "Senha1!" e o papel colado no monitor, com público que digita no celular, no sol)    |
| **S4** — rate limit de login em **10 por 5 min por IP**          | O padrão (30) são 8.640 tentativas por dia por IP. Dez é folgado para quem erra a própria senha, e o limite é por IP — uma fazenda inteira sai pelo mesmo Wi-Fi                                                                                                                                         | Manter 30; captcha (ver abaixo)                                                                                                   |
| **S5** — **sem MFA e sem captcha**, e isto é decisão, não lacuna | MFA exige app autenticador: inviável para quem lança pedido no celular, no sol, e toda troca de aparelho viraria chamado. Captcha adiciona provider externo e falha justamente com sinal fraco, que é o caso comum do funcionário no campo. O ganho equivalente veio de S3 e S4, que custam zero atrito | MFA opcional para o dono (tela de configuração, códigos de recuperação e fluxo de perda de aparelho, tudo às vésperas do go-live) |

**O que sustenta S5**: a superfície real do Lida é pequena — não há
autocadastro (S1), o acesso é criado por uma pessoa conhecida, o RLS
isola cada fazenda, e a senha inicial é obrigatoriamente trocada no
primeiro acesso. Revisar S5 se algum dia existir autoatendimento, ou se
o produto passar a guardar dado que valha um ataque dirigido.

**Nada de auth é caseiro.** Hash, emissão e verificação de JWT, sessão e
troca de senha são do GoTrue; isolamento é RLS do Postgres; as claims
usam o Custom Access Token Hook oficial. Nenhuma tabela nossa guarda
senha — `profiles.senha_definida_em` é um `timestamptz` e registra
_quando_, nunca _o quê_.
